# 분야별 후속 가이드 — 2026-10-28

아이디어 확정 뒤 ‘만드는 법’을 모든 분야에 붙이거나 비음식 기능을 없애는 대신, 아이디어를 발전시킬 수 있는 후속 가이드를 제공한다.

| 분야 | 버튼 | 내용 |
| --- | --- | --- |
| 음식 | 만드는 법 보기 | 재료, 조리 순서, 조리 가능 여부 |
| 프로그램 | 구현 가이드 보기 | 사용자/MVP, 화면·데이터 흐름, 기술 선택, 구현 단계, 기능 검증 |
| 공모전 | 공모전 기획안 보기 | 문제/대상, 해결안·차별점, 시제품·검증, 효과·실현 가능성, 제안서 구성 |
| 직접 만든 카테고리 | 선택한 유형의 가이드, 기본 실행 계획 보기 | 해당 아이디어의 목표, 작은 첫 실험, 필요한 것, 실행 단계, 측정·개선 |

사용자 카테고리 생성 화면에 ‘후속 가이드 유형’을 넣었다. 음식·프로그램·공모전·일반 중 선택하고, 생략하면 general이다. 유형은 `categories.guide_type`에 저장한다. 같은 이름이 이미 있으면 기존 유형을 유지한다. 다른 사람이 만든 공용 카테고리의 유형을 이름만 같은 요청으로 변경하지 않는다.

서버는 `main/app/guide`의 Controller → Service → Component로 분리했다. Service가 조회·생성·캐시·저장을 조합하고, 유형 판단·AI 생성 검증·저장은 각각 Component가 맡는다. DTO는 `core/dto/app/guide`를 사용한다. 기존 recipes 테이블은 저장 호환성을 위해 유지한다.

신규 API는 `POST /app/ideas/{id}/guide`이며 `{guide, cached}`를 반환한다. 기존 `/recipe`도 동일 처리를 하되 기존 응답 구조를 유지한다. 식재료 필드로 개발 준비물을 표현하지 않도록 신규 응답은 `requirements: [{name,detail}]`를 사용한다. 카테고리/아이디어의 `guideType`·`guideLabel`과 아이디어의 `hasGuide`를 화면에 연결한다.

AI 지시문은 유형별로 나눴다. 공모전은 일반 참가 절차가 아닌 해당 아이디어의 문제·차별점·검증 기획에, 프로그램은 해당 아이디어의 실제 최소 기능과 구현·테스트에 집중한다. 반환 유형, 단계 번호·개수·길이, 필수 내용과 공통 내용 정책을 검증한 뒤 저장한다.

기존 음식 레시피는 그대로 읽고, 유형 없는 과거 `plan`은 버튼을 눌렀을 때 새 분야별 가이드로 교체한다. 공유 GET에서는 생성하지 않고 저장된 현재 유형의 결과만 올바른 섹션 제목으로 표시한다. 로컬 기록은 guide 전체를 저장하며 예전 음식 기록도 변환해 읽는다.

DB 변경은 새 Liquibase 이력 `db/v3/001-category-guides.sql`로 추가했다. 기존 이력이나 일반 개발 DB를 직접 수정하지 않는다. 서버를 재시작하면 마이그레이션이 적용된다.

이번 요청 범위에 맞춰 빌드 스크립트·인증 코드는 변경하지 않았다. 검증 시에는 이미 실행 중인 별도 `_test` MySQL 연결을 환경변수로 지정해 백엔드 `build -x demoBuild`를 실행한다. 기본 스크립트의 `pwsh` 탐색 문제를 해결했다고 주장하지 않는다. 실제 기기 설치, 서버 재시작, 실제 Gemini 호출은 하지 않는다.

업데이트 위치: `main/app/guide`, `main/app/recipe` 호환 경로, 카테고리/아이디어 DTO, `demo-web/src/components/IdeaWizard.jsx`·`GuideView.jsx`, `docs/API_SPEC.md`.

검증 결과: 백엔드 `build -x demoBuild` 성공, 테스트 185개 통과·실패/건너뜀 0, 기존 커버리지·스타일 기준 통과. 관련 React 테스트 32개도 통과했다. 실행 중인 서버는 재시작하지 않았으므로 적용 시 백엔드를 재시작한다.
